Task Order — Implementation Planning

Objective

Produce an executable implementation plan for approved downstream or
project-local work. Turn a chosen approach into ordered slices, verification
steps, and explicit stop points without silently expanding scope. A direct
request to change a shared or reusable framework product surface is a framework
candidate, not ordinary planning input; route it through
`task_orders/framework_semantic_audit.md` and
`task_orders/framework_improvement.md` instead.

Procedure

1. Read `AGENT_PROJECT.md`, active state, and the user request. Consult `STATEMENT_OF_WORK.md` only when project-level canonical terms or omitted details matter.
2. Classify ownership before planning. Continue here only for downstream or
   project-local work. A shared or reusable framework-product candidate,
   including one requested directly, routes to report-only framework semantic
   audit and then, only if accepted, framework improvement; generic planning or
   execution authority cannot bypass that route.
3. If scope or acceptance is unclear, load `practice_guides/task_contract.md` first and lock the operative contract.
4. If multiple approaches are still in dispute, stop and use `task_orders/ideate.md` before planning execution unless the User explicitly requests a conditional plan with a hard hold point before implementation.
5. Load `practice_guides/implementation_planning.md`.
6. Produce a compact plan with:
   - objective
   - constraints and assumptions
   - ordered work slices
   - verification and acceptance evidence per slice
   - hold points or approvals
   - residual risks
7. Keep the slices dependency-ordered and evidence-producing. Each slice should make later work safer or clearer.
8. Do not implement the plan unless the User explicitly asks for execution.

Acceptance Criteria

- The approach being planned is already chosen, or the plan is explicitly conditional and stops before implementation.
- The planned work is downstream or project-local; shared or reusable framework
  candidates were routed through semantic audit and framework improvement.
- The plan includes ordered slices with verification.
- Open questions and stop points are explicit.
- Scope expansion is surfaced, not hidden.

Notes

- Use this after ideation, not instead of ideation.
- Use this before delegation, multi-step implementation, or high-coordination work.
- A short low-risk task may need only a 3-line plan.
