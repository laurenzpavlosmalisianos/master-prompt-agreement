Task Order — Scheduled Automation

Objective

Define or revise a standing automation order for recurring agent work. Keep the automation bounded, scheduler-agnostic in concept, and safe to run without a human driving every invocation.

Procedure

1. Read `AGENT_PROJECT.md`, project state, and any existing automation order file. Because this task creates or revises standing automation authority, also consult `STATEMENT_OF_WORK.md` for canonical approval, external-system, VCS, source-acquisition, and automation terms; if `AGENT_PROJECT.md` conflicts with the SOW, the SOW governs.
2. Confirm the recurring objective, cadence, timezone, autonomy level, scheduler context mode, workload class, reviewer boundary, source-access class, and allowed effects.
3. From the framework root, run `scripts/check_prereqs.py` with the approved Python runner if `<runner>` is not already recorded for this project. Use the reported `<runner>` command for stdlib-only framework scripts.
4. Load `practice_guides/scheduled_automation.md`.
5. If `AUTOMATION_ORDERS.json` is absent from the root receipt's mutable-file set, do not create or copy it. Prepare the complete authorized automation configuration as candidate input and route its enablement through `task_orders/framework_refresh.md`; resume here only after verified apply lists the generated manifest and its automation profile in the current receipt. Otherwise update the receipt-declared file in place, preserve its exact `mpa_generated_state_origin` key/value, use the schema-version-7 framework template as the structural authority, and use the [minimum lint-valid disabled draft](../examples/automation_orders.example.json) only as job-content guidance. Record top-level `preferred_backend` as `unspecified` until selected or as one lowercase safe backend slug; the renderer target must match it exactly. Every job declares closed `idempotency`, `state_policy`, and `workload_class` objects or values. Every enabled job declares a closed `authority` object whose basis, effect class, validity, failure action, and verification agree with approval, autonomy, write, and failure fields. A reviewer job requires the `reviewer_runtime_class`/`reviewer_boundary_mode` pair; `external` additionally requires `external_review`. Every source-reading job declares `source_access_class`; a non-public class requires `source_policy`, while public unauthenticated access forbids it. `parser_change` is required exactly for `workload_class: parser_or_extractor_change`. Descriptive prose never activates or satisfies these policies. Keep `cwd` portable. Under `scheduler_artifacts`, declare a confined root, root-relative log and lock, finite `max_log_bytes`, and closed `retention` and `redaction` objects. Set `lock_file` to `null` only when concurrency is `allow`.
6. Keep each job narrow: one objective, one schedule, one authority boundary.
7. Keep reusable procedure in framework or project modules. Declare each source as a closed `root`/`path` object, with `root` exactly `framework` or `project`; there is no fallback. Every job binds the fixed framework instruction closure `task_orders/automation.md` plus `practice_guides/scheduled_automation.md`; including `runtime/task_modules/automation.md` does not replace either dependency. Use `instruction_sources` for additional Task Orders, Practice Guides, template briefs, and project-local additions under the fixed `local_overlays/` root. Use `execution_sources` for scripts, wrappers, local modules, configuration, and dependency lockfiles that materially define command execution. An empty execution list asserts that the command consumes no project/framework execution file. Keep scheduler prompts and commands thin; do not use a shallow shell-text parser as evidence that the list is complete.
8. Select the narrow owning project's explicit absolute `<project-root>` at lint/render time, not a common ancestor chosen to make unrelated paths appear contained. Let `<manifest>` be the `AUTOMATION_ORDERS.json` owned by that project; it may be at the project root or a nested contract root. The manifest and every job's resolved relative `cwd` must each remain inside `<project-root>`. Neither containment relationship substitutes for the other, and host-specific project paths do not belong in the portable manifest.
9. From the downstream project root, resolve `<framework-ref>`, `<manifest>`, and `<project-root>`, then run `<runner> -- "<framework-ref>/scripts/automation_orders_lint.py" <manifest> --project-root <project-root>` on the manifest.
10. If `preferred_backend` is `cron` and the User requested cron rendering, run `<runner> -- "<framework-ref>/scripts/automation_orders_lint.py" <manifest> --project-root <project-root> --target cron` before rendering. Do not select a renderer that disagrees with `preferred_backend`.
11. If the User requested a `cron` backend and the cron target check passes, run `<runner> -- "<framework-ref>/scripts/render_cron.py" <manifest> --project-root <project-root> --output <temporary-cron-file>` to generate a temporary review artifact in an approved temporary location, outside the project root only when the project or runtime boundary authorizes it.
12. Treat scheduler rendering as backend-specific and separate from installation or enablement. The cron renderer accepts only the current typed Cronie-compatible profile and emits the framework runtime helper with its current sealed launch profile. Apply the detailed seal, cache-isolation, descriptor, artifact, process-group, retention, limitation, and unsupported-semantics contract from `practice_guides/scheduled_automation.md`; that guide is the detail owner and this Task Order supplies the procedural gates.

Acceptance Criteria

- The standing automation order is explicit about authority, scope, and failure handling.
- Every enabled job has a typed `authority` contract with allowed action and resource references, grant basis, effect class, validity and revocation events, failure action, and verification evidence; the typed values agree with the job's approval, autonomy, write, and failure settings.
- Every enabled cron job uses a standing-project grant; a disabled `per_run` draft may be stored but cannot render or execute.
- Reusable procedure and execution files are loaded through explicitly rooted instruction and execution sources, not ambiguous fallback or duplicated scheduler prompts, project-local automation text, or external reviewer prompts.
- Scheduler-created artifacts and retention satisfy the complete `practice_guides/scheduled_automation.md` contract. In particular, retention governs the log rather than the active coordination lock, manual handling requires disablement or uninstallation plus proven invocation quiescence, and deterministic field checks do not prove that a named owner or trigger is operationally adequate.
- The job states `fresh_run` or `thread_continuity` and declares `state_policy` with closed persistence, checkpoint, resume, and reference values. Thread continuity requires persistent state, a checkpoint, or cursor resume; neither thread state nor descriptive prose supplies authority.
- A scheduled job cannot create, edit, pause, resume, delete, or broaden other scheduled jobs unless that control-plane task is the exact approved objective and a separate verification gate checks the result.
- Reviewer jobs declare the closed runtime/boundary pair. External jobs use `external_review` to enumerate allowed data classes and closed authentication, egress, redaction, retention, artifact, request-cap, sensitive-data, and unlisted-data decisions; both sensitive and unlisted data are denied. Non-public source jobs use `source_policy` for neutral aliases, read capabilities, exact scopes, request and retention bounds, dated terms review, denied writes, and required primary-source verification.
- The manifest passes lint.
- If a scheduler backend was requested, `preferred_backend` agrees with it and target compatibility passes before rendering.
- If a scheduler backend was requested, the temporary rendered file exists and matches the manifest for that backend.
- Installing or enabling the rendered schedule is separately authorized and verified only when installation or enablement was actually requested and approved.

Notes

- Prefer `observe` or `propose` automation before `act`.
- Current-only cutover: if a retained manifest predates schema v7, first disable or uninstall its schedule and prove all invocations quiescent. Prepare and review a direct v7 replacement using current authority, lint it, then freshly render, review, and reinstall any requested backend entry. Do not translate aliases or add a compatibility path.
- `act` automation should exist only when the standing automation rule is explicit and the rollback or escalation path is clear.
