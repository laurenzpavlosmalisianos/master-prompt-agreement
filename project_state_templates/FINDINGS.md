# Framework/Process Findings

_Optional project-local observations about framework effectiveness, rule friction, process gaps, redundant work, missing shared sources, and measured effects._

Use this file as input to `task_orders/insights.md`, not as a public framework change log and not as the ordinary output file for code-review, audit, scanner, or standards defects. Raw framework/process findings stay project-local. If a finding becomes a shared framework candidate, move only the sanitized abstraction into `FRAMEWORK_FEEDBACK.md`: remove environment-specific paths, project names, issue IDs, branches, commit hashes, secrets, identities, raw logs, private code, proprietary context, and one-off anecdotes; keep only the reusable pattern, evidence scope, affected framework surface, proposed change, applicability, and non-goals.

Keep only findings that remain unresolved or still serve a current independent
evidence role. After a finding is fixed, rejected, or superseded, first ensure
that the applicable insights or maintainer review has consumed it and that any
reusable lesson or no-action rationale is owned by a rule, decision, source
record, regression test, or concise recurring precedent. The duplicate finding
body then becomes a removal candidate under the project's deletion and backout
authority once its required disposition evidence is already retained or will
be recorded by the same reviewed atomic version-control or archive change.
Before finalizing that change, inspect the replacement owner, retained evidence,
exact staged or archive payload, and backout path together. Do not retain routine
failures or command logs as project history, and do not remove the sole evidence
supporting an active claim, obligation, incident review, or unresolved safety
concern.

_Format: date, finding, category (Mistake / Help / Hinder / Missing), detail, scope (project / framework candidate), evidence._
