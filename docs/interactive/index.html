Architecture

Runtime and lifecycle routes

Ordinary task route

  1. Root context

    Resolve platform limits, the user task, the selected framework checkout, and the governed project root without loading generated project authority.

  2. Recovery gate

    For an existing project, read the selected charter and then check the governed project root for the closed journal, lock, and recovery-temp control set before generated authority or state; any control stops ordinary work.

  3. Project contract

    Only after the recovery gate is clear, load AGENT_PROJECT.md or the configured generated contract. Consult the SOW when routed for canonical or omitted terms, full task-specific checklists or acceptance terms, ambiguity, or contract revision.

  4. Runtime packet

    Interpret the user request under the project contract, then check state headers and load only task-relevant records. Add only task-conditioned guidance and evidence.

  5. Specialist guidance

    Use a runtime task module for a known workflow or the full Task Order when needed; add only relevant Practice Guides.

  6. Evidence and verification

    Inspect files, diffs, logs, sources, and generated output before claims; run checks where objective invariants can be tested.

  7. Learning

    Treat source, review, and feedback output as candidate evidence. Route reusable framework candidates through report-only semantic audit, then route only accepted candidates through Framework Improvement; keep project-local changes on their project route.

Existing-instance lifecycle routes

Instances with a verified complete current-format identity pair and intact recorded preimage may enter reviewed refresh planning; a successful apply must then reach exact-current acceptance. Closed transaction controls instead permit only exact-ID recovery, while a verified approved plan may permit a bounded post-success restore. Ordinary project work does not enter any of these routes.

  1. Plan and backout basis

    Inspect without writing and create one canonical plan. The plan selects either the normal verified exact-preimage bundle or, only where permitted, the explicit no-post-apply-backout exception; mutable-state retirement requires the bundle.

  2. Approval and acceptance

    Approve the exact plan digest and every required action or warning, apply once, verify every active profile, and inspect for exact-current acceptance.

  3. Restore or recover

    Post-success restore exists only for the verified-bundle branch while the live postimage still matches. Interrupted transactions instead enter the separate closed-control route and permit only the reported exact-ID recovery action.

Quality gates

Verification does not replace judgment

Scripts

Objective check

Check schema, generated output, links, state, routing, rendering, and configured file-size ceilings.

Semantic review

Requires judgment

Decide semantic fit, ownership, source abstraction, and architectural coherence; proportional improvement evaluates incremental output value.

Reviewer lanes

Requires judgment

Challenge narrow evidence packets without granting authority to reviewer output.

Project boundaries

Objective check

Check that generated files match declared paths, registered integrations, project identity, and state-record contracts.
